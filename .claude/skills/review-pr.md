# PR コードレビュー

プルリクエストまたは現在のブランチの変更をレビューしてください。

## 引数

- `pr_number_or_branch`（任意）: PR 番号またはブランチ名。省略時は現在のブランチの差分をレビューする

## 手順

### 1. 差分を取得する

```bash
# PR 番号が指定された場合
gh pr diff <pr_number>

# ブランチ名が指定された場合
git diff main...<branch>

# 省略時
git diff main...HEAD
```

### 2. 以下の観点でレビューする

#### アーキテクチャ（AGENTS.md 準拠）

- domain 層に外部依存（firebase-admin, stripe 等）が混入していないか
- 依存方向: domain ← application ← infrastructure / app
- 集約境界が守られているか（集約の外からメンバーを直接変更していないか）
- 集約をまたぐ処理が UseCase を経由しているか

#### 型安全性

- `any` 型が使われていないか
- 適切な型定義がされているか（`type` 推奨、`interface` は外部公開 API のみ）
- `as` によるキャストが不要に使われていないか

#### コーディング規約

- ファイル名が kebab-case か
- Repository Interface が `i` プレフィックスを持つか
- コンポーネント名が PascalCase か

#### フロントエンド（該当する場合）

- `"use client"` が不要に付いていないか（Server Component がデフォルト）
- UI コンポーネントが `@/components/ui` から import されているか
- Panda CSS のトークンやレシピが適切に使われているか

#### セキュリティ

- 機密情報（API キー、シークレット）がハードコードされていないか
- ユーザー入力のバリデーションが適切か
- SQL インジェクション / XSS のリスクがないか

#### パフォーマンス

- 不要な再レンダリングを引き起こすパターンがないか
- N+1 クエリのリスクがないか
- 大きなバンドルサイズへの影響がないか

## 出力形式

```markdown
## レビュー結果

### 問題あり（要修正）
- [ファイル名:行番号] 問題の説明と修正案

### 提案（任意）
- [ファイル名:行番号] 改善の提案

### 良い点
- 良かったポイント
```

## ルール

- 重要度順に報告する（アーキテクチャ違反 > 型安全性 > セキュリティ > パフォーマンス > 規約）
- 具体的なファイル名と行番号を示す
- 修正案は実際のコードで提示する
- 良い点も必ず挙げる（レビューはフィードバックのバランスが大事）
